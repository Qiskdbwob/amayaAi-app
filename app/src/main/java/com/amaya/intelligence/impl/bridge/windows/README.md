# `impl/bridge/windows` — Android Windows Bridge Client (Phase 2)

This package implements the Android-side transport client that talks to a Windows
Bridge peer using the Phase 1 shared protocol declared in
`com.amaya.intelligence.domain.bridge`.

## Scope

Phase 2 only introduces the transport. It does **not**:

- implement Electron, the native Windows helper, or any Windows-side executor;
- integrate with the AI planner / agent loop on Android;
- render any UI (approval, chat, screen stream);
- touch the existing local chat flow, Antigravity remote flow, browser operator,
  memory, skills, or self-improvement subsystems.

The Antigravity client in `impl/ide/antigravity/client/RemoteSessionClient.kt` is
used as an inspiration for WebSocket lifecycle, reconnect/backoff, sequence handling,
and command queueing, but none of its Antigravity-specific code is reused here.

## File map

| File | Purpose |
| --- | --- |
| `WindowsBridgeSessionClient.kt` | Public client: connect/disconnect/send/receive, reconnect loop, seq tracking, outbound queue. |
| `WindowsBridgeClientConfig.kt` | Connection parameters (host, port, token, device/session id, reconnect policy). |
| `WindowsBridgeConnectionState.kt` | High-level transport state enum. |
| `WindowsBridgeClientEvent.kt` | Sealed hierarchy of client → consumer events. |
| `WindowsBridgeEventHandler.kt` | Optional callback surface for consumers that don't subscribe to `events`. |
| `WindowsBridgeEnvelopeMapper.kt` | Tolerant JSON ↔ `BridgeEnvelope` mapper with typed decoders. |
| `WindowsBridgeLogger.kt` | Centralized logging. Never logs raw payloads or tokens. |

## Wire format

All frames are JSON objects shaped like `BridgeEnvelope`:

```json
{
  "id": "msg_001",
  "type": "tool.call",
  "sessionId": "session_abc",
  "deviceId": "android_123",
  "seq": 42,
  "timestamp": 1778320000,
  "payload": { }
}
```

The mapper accepts unknown payload keys and unknown message types without throwing:
unknown types produce a `DecodeResult.Failure`, which the client surfaces as
`WindowsBridgeClientEvent.Error` rather than crashing.

## Sequence handling

- Outgoing envelopes carry a monotonically increasing `seq` generated by the client.
- Incoming envelopes with `seq <= 0` are accepted without dedupe.
- Duplicate `seq` values (equal to the last seen) are dropped.
- Gaps (`seq > lastIncoming + 1`) are logged but not healed. A real replay/ack
  protocol will come in a later phase.

## Pairing

Phase 2 only plumbs the plumbing:
- `X-Amaya-Device-Id` and optional `Authorization: Bearer <token>` headers are sent
  on the WebSocket handshake;
- `device.paired` / `device.disconnected` events are surfaced to consumers;
- no QR or pairing UI lives here yet.

## What the next phases add

- Phase 3: agent integration — the planner issues `BridgeToolCall`s through this
  client and consumes `ToolResultReceived` / `ApprovalRequestReceived` events.
- Phase 4+: approval UI, audit storage, QR pairing, foreground service, and
  session persistence.
